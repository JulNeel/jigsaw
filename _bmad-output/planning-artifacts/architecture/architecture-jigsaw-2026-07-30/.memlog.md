- (decision) Paradigme: architecture locale-first / sync optimiste. Client = TanStack DB (collections reactives, mutations optimistes avec rollback auto). Sync = ElectricSQL (Shapes Postgres, un Shape par Salon). Postgres = source de verite unique. Prevents: divergence d'etat entre clients, logique de sync ad-hoc reinventee par ecran
- (decision) Validation metier FR-6 (correspondance reelle des decoupes) vit cote serveur (write-path), jamais dans Electric qui ne gere que la synchronisation en lecture
- (decision) Hebergement: Supabase pour Postgres + Auth (integration native Electric) + Storage (upload photos FR-18). Reduit le nombre de services geres par le dev solo
- (constraint) Electric necessite la connexion directe Postgres de Supabase (pas le pooler) pour la replication logique - IPv6 ou add-on IPv4 (plan Pro/Team) requis
- (decision) Write-path: Server Actions/API routes Next.js (colocalise avec le front, pas de service backend separe). Un futur client non-web consommerait les memes routes HTTP sans changement d'architecture
- (decision) Rendu canvas: Konva.js + react-konva (meilleure integration React/drag-drop que PixiJS pour ce volume de pieces)
- (decision) Decoupe des pieces: service serveur (Node, dans les Server Actions) declenche a la creation du Salon (FR-17-20). Algorithme deterministe a graine (courbes de Bezier a languettes). Produit: silhouettes, graphe d'adjacence (vrais voisins + categorie forme elementaire), tuiles PNG stockees Supabase Storage. Le graphe d'adjacence precalcule est la base de la validation FR-6 (lookup au lieu de calcul geometrique a la volee)
- (decision) Hebergement: Vercel pour le web Next.js (deploiement zero-config, preview par PR). Wrapper mobile Capacitor distribue separement sur les stores. Environnements: dev/preview/production classiques (Vercel preview natif par branche; Supabase projet separe ou schema isole pour dev)
- (decision) Nommage: code en anglais (contrairement au francais des specs PRD/UX). Table de correspondance obligatoire pour eviter la derive: Salon->Room, Cadre->Frame, Espace infini->Canvas, Ilot->Cluster, Invite->Guest, Participant->Participant, Forme elementaire->PieceShape (Corner/Edge/Interior)
- (decision) IDs: UUID v4 (natif Postgres gen_random_uuid()). Dates: timestamptz Postgres / ISO 8601. Mutations: jamais d'ecriture directe client vers Postgres, tout passe par les Server Actions Next.js (seul point d'application de la validation FR-6)
- (direction) ERD envisage: Room, Participant, RoomParticipant (jointure, isGuest), Piece (shape, gridPosition, imageAssetRef, position, placedInFrame), PieceAdjacency (vrais voisins precalcules), Cluster (Ilot), ContributionEvent (historique/stats)
- (event) Spine distille (Design Paradigm, AD-1 a AD-5, Consistency Conventions, Stack, ERD, arborescence, Deferred)
- (decision) AD-6 ajoutee: resolution de conflit FR-7 = dernier-arrive-gagne au niveau transaction Postgres, rollback optimiste cote perdant, pas d'ecran de conflit dedie
- (decision) AD-7 ajoutee: presence FR-12 via table RoomPresence synchronisee par le meme canal Electric (pas de canal separe, coherent avec AD-1)
- (constraint) AD-2 durcie: RLS deny-by-default sur les tables de domaine, aucun droit d'ecriture anon/authenticated - empeche techniquement l'ecriture client directe, pas seulement par convention
- (version) Next.js 16.x (15.x en maintenance). ElectricSQL >= 1.5.0 obligatoire (CVE-2026-40906 injection SQL critique sur /v1/shape, corrigee en 1.5.0)
