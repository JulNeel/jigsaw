# Story 2.4: Create the Room and get a shareable invite link

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a registered Participant,
I want to finalize my Room and receive a public invite link,
so that I can immediately send it to my household and let them join.

## Acceptance Criteria

1. When the Participant confirms creation (with a chosen image and a valid piece count), the deterministic piece-cutting service runs once, producing each Piece's `PieceShape` (Corner/Edge/Interior) and the `PieceAdjacency` graph of true neighbors, with image tiles written to Supabase Storage.
2. A public invite link is generated and displayed with a "Copy" action and share shortcuts (WhatsApp, email), matching `key-creation-salon.html`'s second state.
3. The invite link resolves to a fully-prepared Room record — pieces already cut, `PieceAdjacency` graph ready — with no generation delay for whoever opens it later (the joining experience itself is Epic 3's job; this story only guarantees the data is ready).
4. All pieces are scattered at random positions on creation — never pre-arranged or pre-sorted — so the first Participant to arrive finds a genuinely unsolved puzzle.

## Dev Notes — read before starting, several foundational decisions are made here

- **User-confirmed scope decision (2026-08-14): rectangular grid pieces, not curved interlocking tabs.** `PieceShape` (Corner/Edge/Interior) is a **grid-position classification** (how many grid edges of a piece are on the Room's outer boundary), not a visual tab/blank curve shape. Every piece is cut as a plain rectangle. This was an explicit, deliberate simplification — the Architecture spine itself flags exact tab curvature/tolerance as an undecided implementation detail, and building real curved-tab geometry would need a server-side image library (`sharp`, none installed) or heavy client-side canvas path clipping, disproportionate to this story. Real puzzle-shaped rendering (if ever wanted) is a future decision for whoever builds Epic 3's Canvas rendering — this story's data model does not block that; a later story could reslice with real tab curves without changing `PieceShape`'s three-value classification.
- **This is the first story to create real domain tables.** `Room`, `Piece`, `PieceAdjacency` land here (Epic 2, as the baseline migration always said they would). Follow Architecture AD-2 exactly: all three tables are written **only** via one Server Action using a direct Postgres connection (service-level), never via the Supabase client SDK's `.from(table)`. The Supabase client SDK is used in this story **only** for Storage uploads (client-side, explicitly permitted by AD-2 alongside Auth) — never for Room/Piece/PieceAdjacency writes.
- **No `Participant`/`RoomParticipant` table yet** — `Room.created_by` is a plain `uuid references auth.users(id)`. Still no separate Participant table needed (same restraint as Stories 1.4/2.1); Epic 4 introduces it when Guest-to-Participant conversion needs it.
- **Grid layout is derived, not literally the requested piece count.** `PIECE_COUNT_OPTIONS` (Story 2.3) are nominal targets (100/300/500/1000/1500); the actual grid is `cols = round(sqrt(nominalCount * aspectRatio))`, `rows = round(nominalCount / cols)` (both clamped to ≥1), so the cut always forms a clean rectangle matching the image's aspect ratio. The **actual** piece count (`rows * cols`) may differ slightly from the nominal option (e.g. "500 pieces" might actually cut 504) — this is expected and documented, not a bug. Store both: the nominal `piece_count` the Participant picked (for display/consistency with Story 2.3) and the real `grid_rows`/`grid_cols` (source of truth for actual piece count = `grid_rows * grid_cols`).
- **"Deterministic, seeded" (Architecture AD-3) applies to the scatter positions, not the cutting itself.** For a plain rectangular grid, shape classification and adjacency are already 100% deterministic from `(row, col, rows, cols)` — no randomness involved, nothing to seed. The *only* randomness in this story is where pieces initially land (AC #4), which uses a small seeded PRNG (seeded by the Room's id) so a given Room's initial scatter is reproducible if ever needed for debugging, while still looking random to Participants.
- **Scatter coordinate space is provisional — Epic 3 owns the real infinite-canvas/Frame layout, which doesn't exist yet.** This story stores `scatter_x`/`scatter_y` as plain numbers representing an arbitrary canvas-pixel space centered on the Frame's origin (random angle + radius in a fixed range around `(0,0)`). Whoever builds Epic 3's actual Canvas/Frame positioning may need to reinterpret or migrate these values once a real coordinate system exists — that's expected, not a defect introduced here.
- **Invite link uses a human-readable slug, not the raw Room UUID** — matches `key-creation-salon.html`'s example (`jigsaw.app/salon/famille-dupont-8k2p`). `Room.id` (UUID) stays the internal primary key; a separate unique `invite_slug` column (slugified name + short random suffix) is the public identifier used in the URL. The existing `src/app/room/[id]/page.tsx` stub (Story 1.1) is reused as-is for this route — its dynamic segment now conceptually holds the slug, looked up via `WHERE invite_slug = $1`, not a UUID lookup. (Fully wiring that page's real content is Epic 3's job; this story doesn't touch it beyond this lookup-semantics note.)
- **The `piece-tiles` Storage bucket already exists (private, created in Story 1.1)** but nothing has used it yet — it very likely has no upload policy configured. Task 1 below includes a guided check/setup step (same pedagogical pattern as prior Supabase Dashboard steps: I cannot access your dashboard, so this needs you to confirm/create it).
- **Unauthenticated (Guest) read access to Storage tiles is explicitly out of scope for this story.** The bucket is private; Epic 3 (where Guests first need to actually see tile images) will need to solve read access (a Storage read policy, or signed URLs) — noted as a forward reference in `deferred-work.md`, not solved here, since no Guest-facing rendering exists yet to test it against.
- **No domain-table Vitest coverage for the Server Action's database work** — following the same reasoning as `signUp`/`signIn`: the Postgres-touching branch is integration-level, verified manually/via script against the real database (Task 7), while all pure logic (grid math, shape classification, adjacency, slug generation) is unit-tested in isolation.

### Review Findings

- [x] [Review][Patch] `createRoom` trusts the client's `shapeType` and grid position (`row`/`col`) verbatim instead of recomputing/validating them server-side — inconsistent with `computeAdjacency`, which *is* recomputed authoritatively. A malicious/buggy client could persist an incorrect `PieceShape`, out-of-range position, or duplicate `(row, col)` for its own Room [src/lib/rooms/actions.ts]
- [x] [Review][Patch] Uploaded tiles are never cleaned up if `createRoom` fails after upload (slug-retry exhaustion, DB error, or the user abandoning the tab mid-flow) — permanent Storage leak with no compensating delete [src/app/create/create-room-form.tsx, src/lib/rooms/upload-piece-tiles.ts]
- [x] [Review][Patch] Double-submit race: `isSubmitting`'s state update can lag a render behind a rapid double-click/double-Enter, and `canSubmit` doesn't check `imageDimensions !== null` the way `handleSubmit`'s guard does — both a possible double Room creation and a "dead click" window where the button is enabled but does nothing [src/app/create/create-room-form.tsx]
- [x] [Review][Patch] `createRoom` inserts every piece and every adjacency pair with its own awaited round-trip inside one open transaction (1500+ sequential inserts for the largest piece count) — directly relevant to the "very long" creation time already reported and partially fixed (tile upload parallelization); batch into multi-row `INSERT ... VALUES` statements instead [src/lib/rooms/actions.ts]
- [x] [Review][Patch] `generateInviteSlug`'s random suffix isn't guaranteed to be 6 characters (`Math.random().toString(36)` can be shorter), and truncating the slugified name at 60 chars can leave a trailing hyphen, producing slugs like `name--ab1` or a suffix shorter than documented [src/lib/rooms/generate-invite-slug.ts]
- [x] [Review][Patch] The adjacency-pair loop silently `continue`s when a `(row, col)` isn't found in `pieceIdByPosition` instead of erroring — a malformed/incomplete piece payload would commit a Room with a silently incomplete `PieceAdjacency` graph rather than failing loudly [src/lib/rooms/actions.ts]

- [x] [Review][Patch] `isMountedRef` is only checked before `setIsSubmitting(false)` in the `finally` block — `setSubmitError`/`setSuccessResult` earlier in the same async flow don't have the same guard, inconsistent with the pattern established elsewhere in this component [src/app/create/create-room-form.tsx]

- [x] [Review][Patch] No `CHECK` constraint ties `image_source`/`image_library_id` together — a row with `image_source = 'upload'` and a populated `image_library_id` (or `'library'` with a null one) is fully insertable [supabase/migrations/20260814000000_rooms.sql]
