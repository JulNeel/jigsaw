# Story 3.6: Placement feedback

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Participant who just placed a piece,
I want an immediately satisfying visual and sound response,
so that contributing feels rewarding in the moment.

## Acceptance Criteria

1. Given a successful piece (or Cluster) placement — a piece/Cluster locking into the Frame via `placePiece` (Story 3.5/3.8/3.9) — when the piece snaps into the Frame, then a micro-animation and a wood-click sound play, paired with a haptic tick on mobile (where supported — see Dev Notes on `navigator.vibrate` platform support).
2. The sound can be muted/unmuted independently by each Participant, via a control that stays accessible at all times (not buried in a submenu) and carries an accessible name.
3. The visual feedback still occurs when sound is muted — sound is never the only signal (NFR2, accessibility floor).
4. `prefers-reduced-motion` reduces the micro-animation to a simple state change with no motion.
5. This fires for every Participant present in the Room when *any* piece/Cluster locks in (not only the one who dropped it) — the collaborative, shared-table feel this app is built around; each Participant's own mute preference still governs whether *they* hear it (see Dev Notes' User-confirmed scope decisions for why).
6. The placement is also announced via an `aria-live="polite"` region, decoupled from canvas manipulation, so a screen-reader user perceives the Room's activity without needing to interact with the canvas (EXPERIENCE.md's Accessibility Floor).

## Amendment (2026-09-02): sound model revised twice, user feedback

AC #1's original scope only ever covered a single sound, tied exclusively to a confirmed Frame lock-in. Revised after user feedback, post-review, in two passes:

7. **A generic "piece released" sound (the existing wood-click) plays on every drag-end release, anywhere on the Canvas** — in the Frame, fused elsewhere, or a plain free-space move — never gated on whether a match was attempted or achieved. Represents the tactile "setting a piece down," not a validation signal.
8. **A distinct, bright success chime layers on top of the drop sound** when the drop was a genuine Frame lock or a genuine fusion match — fired from the *client-side prediction* (`predictFrameLock`/`predictFusionOutcome`), not a wait for server confirmation, consistent with Story 3.11's whole premise of instant, reliable feedback. Purely cosmetic/non-authoritative, same as every other prediction in this app — the server's own re-validation is what actually decides the write, regardless of which chime played.

**~~9. A distinct reject thud layers on top of the drop sound when a match was attempted and failed.~~ Removed entirely (2026-09-02, user feedback), not deferred or silenced conditionally — there is no reject sound in this app at all.** A failed or untested attempt only ever gets the drop sound (or nothing extra, if it wasn't even a genuine attempt — see below); success is signaled, failure/uncertainty never is. `playRejectThud`/`rejectThudEnvelope` were removed from `play-tone.ts` outright rather than left unused.

**Refined between the two passes above:** not every Frame-slot drop is a genuine "validation attempt" for AC #8's purposes — AD-3's physical-puzzle leniency means an edge/interior piece with no already-placed neighbor to test against is neither confirmed nor rejected by `placePiece`, it just rests untested. The only two scenarios that count as a genuine Frame validation attempt: **(1)** a genuine corner-shaped piece dropped at a grid-corner slot, or **(2)** a drop landing adjacent to at least one already-placed (validated) neighbor, regardless of shape category. `predictFrameLock` returns `{ locked, isValidationAttempt }` to carry this distinction — the success chime only ever fires when both are `true`. Fusion is unaffected by this distinction — Story 3.8's fusion rule has no equivalent bootstrap leniency (every genuine contact is meant to be tested immediately), so every contact attempt there already qualifies as a genuine attempt; it just never had a reject sound to remove, since it lost that in the pass above.

## User-confirmed scope decisions (2026-09-01)

- **Fires for every Participant present, not just the actor.** Neither FR-14 nor this epic's AC text says so explicitly, but the surrounding evidence is decisive: FR-14's mute setting is described as *per-Participant* ("chaque Participant"), which only makes sense if the feedback would otherwise reach everyone; Story 3.7 (Celebrate a completed Frame) explicitly states its celebration is "visible to every Participant present... not only the one who placed the last piece" — the same collaborative philosophy, one level down. Reusing the Realtime stream every client already subscribes to (Story 3.5's `postgres_changes` on `piece`) is also the only way to know a *remote* Participant's placement happened at all, without inventing a second channel (AD-1 forbids that outright). Revisit if real-family testing shows constant sound from others' actions is more annoying than rewarding.
- **No audio asset files exist in this repo yet** (`public/` has none). Rather than sourcing/licensing external samples for a solo-dev project, the "wood-click" and any future "electronic victory" (Story 3.7) sounds are synthesized at runtime via the Web Audio API (a short filtered-noise burst with a pitch/amplitude envelope, tuned to read as an organic knock rather than a synth beep) — zero asset files, zero licensing surface, adjustable in code. Reasonable default, not spec-mandated; revisit with a real sample if the synthesized result doesn't read as "wood" in practice.
- **Mute preference persists in `localStorage`, per-browser, not synced to the account or Room.** FR-14 doesn't specify persistence duration; nobody wants to re-mute on every visit, and there's no server-side concept of "this Participant's sound preference" anywhere in the schema — inventing one would be sync surface this purely-cosmetic preference doesn't need (AD-1's "no parallel channel" spirit extends naturally to "no parallel synced setting" for something with zero gameplay effect).
- **`navigator.vibrate()` has no iOS Safari support at all** (confirmed current platform behavior, not project-specific) — likely relevant given this app's family/household audience skews toward iOS devices (already flagged as a real risk earlier in this epic, re: canvas API choices). Treated as progressive enhancement: feature-detected, silently a no-op where unavailable. Never blocks or degrades the visual/sound feedback.
- **`aria-live` scope narrowed to placement events only, not the full Accessibility Floor bullet.** EXPERIENCE.md's Accessibility Floor bullet also covers "Participant joins/leaves" — out of scope here (that's Story 4.1's Live Presence territory); this story only wires the announcement for piece/Cluster placement, since that's what FR-14 actually governs. Revisit/extend when Epic 4 builds presence.
- **Detection of "a placement just happened" (the sound/pulse/haptic/`aria-live` feedback, AC #1/#5/#6) is client-side, sourced from a confirmed-only Realtime event — not a diff of the optimistic collection snapshot.** ~~Original version diffed the live piece-collection snapshot across renders (a `useRef`-held set of previously-placed piece ids)~~ — corrected by code review (2026-09-02): that diffed the *optimistically*-blended snapshot, firing on unconfirmed/rejected attempts too. `src/lib/rooms/piece-placement-events.ts` now emits only from `collections.ts`'s Realtime sync handler, which never runs on an optimistic guess. Still not a new Server Action or schema change — purely an additional client-side event channel over the same Realtime stream every client already subscribes to. (The *drop/success/reject sound layer* added in the 2026-09-02 amendment above is deliberately the opposite: instant and prediction-based, not confirmation-gated — a different signal for a different purpose.)

## Dev Notes

### Why this story has no server-side changes at all

Every prior story in this epic (3.5, 3.8, 3.9) changed `piece-actions.ts`, the schema, or both — this one deliberately doesn't. Placement feedback is a reaction to state that's already fully synced and validated (AD-2's server-authoritative rule already governs *whether* a piece gets placed; this story only decorates the moment the client observes that having happened). Introducing a new Server Action or DB column for "should I play a sound" would be scope creep with no gameplay purpose.

### Where this plugs into `room-canvas.tsx` and `room-view.tsx`

`RoomCanvas` already computes `pieces` from `useLiveQuery` (Story 3.5) and knows `frameWidth`/`frameHeight`/`tileWidth`/`tileHeight` for positioning. The "newly placed" diff (Task 3) reads that same array — no new subscription, no new collection.

The new mute button mounts in `src/components/room/room-view.tsx`, as a sibling of the existing `<RecenterButton>` (same Room-level chrome overlay, not canvas content):

```tsx
<RoomCanvasClient ref={canvasRef} room={room} onReady={() => setCanvasReady(true)} />
<RecenterButton onClick={() => canvasRef.current?.recenter()} disabled={!canvasReady} />
{/* new: <SoundMuteButton /> or similar, same sibling level */}
{isGuest && <FirstAccessTutorial roomSlug={roomSlug} canvasReady={canvasReady} />}
```

Unlike `RecenterButton`, the mute button needs no `canvasReady`/`ref` wiring — it only ever touches `localStorage`, independent of canvas state. The `aria-live` region can live either here or inside `RoomCanvas` itself (wherever it's simpler to reach the newly-placed-piece diff from Task 3); `RoomCanvas` is more natural since that's where the diff already happens.

Unrelated pre-existing note, not this story's concern: `RecenterButton`'s `disabled={!canvasReady}` in this exact file is the source of a known (separately tracked, not yet fixed) SSR hydration mismatch — don't let it distract from this story's own changes, and don't fix it here (scope creep).
