# Story 3.12: Real puzzle-piece cut shape

Status: done

## Story

As a Participant,
I want each piece to actually look like a cut puzzle piece (tabs and blanks along its edges), not a plain rectangle,
so that the Room feels like a real jigsaw puzzle, not a sliding-tile grid.

## Acceptance Criteria

1. **Given** the Room's Frame is `rows × cols`, **when** any piece is rendered anywhere in the Canvas (loose, mid-drag, fused into a Cluster, or locked into the Frame), **then** it displays a tab/blank silhouette on each of its interior edges (a bump protruding outward, or a matching notch cut inward), deterministically the same every time the Room is loaded.
2. Every pair of orthogonally-adjacent pieces' shared edge shows complementary shapes — one piece's tab is exactly its neighbor's blank at that edge.
3. An edge on the Frame's outer boundary (per `classifyPieceShape`'s existing Corner/Edge/Interior classification — a piece has no neighbor on that side) renders flat/straight, never a tab or blank.
4. A piece's rotation (Story 3.5, fixed 90° increments) rotates its tab/blank silhouette together with its image as one rigid shape — correct at 0°/90°/180°/270°, not just 0°.
5. This is a purely cosmetic rendering change: FR6's placement/fusion validation (`PieceShape`, `PieceAdjacency`, `validate-placement.ts`, `validate-fusion.ts`) is completely unchanged. A piece still locks in or fuses based on the existing grid-position/adjacency rules — never based on the new visual silhouette. No Server Action, schema, or migration is touched.
6. A piece that hasn't loaded its image yet, or whose image failed to load, still shows *some* silhouette outline (the existing loading/error placeholder states from `PieceSprite`, Story 3.1) — the new masking must not crash or blank out these fallback states.

## Dev Notes

### Why a client-side mask, not a real re-slice — and why that's not a downgrade

Confirmed with the user before this story was written (2026-09-03): two approaches exist for a jigsaw piece to actually look cut (tabs/blanks) instead of a plain rectangle.

- **Chosen: client-side rendering mask.** The stored tile images stay exactly as `slice-image.ts` produces them today (plain rectangular cuts, Story 2.4's own scope decision — see its Dev Notes). At render time, `PieceSprite` applies a Konva `clipFunc` — a vector clip path following the piece's tab/blank silhouette — so only the correctly-shaped portion of the (still-rectangular) image is visible.
- **Rejected: real server-side re-slice.** Story 2.4's own Dev Notes originally imagined "a future story could reslice with real tab curves" as the way this would eventually be solved — that assumption is explicitly superseded here. A real re-slice would need an image-manipulation library not currently installed (e.g. `sharp`), would touch the Storage/creation pipeline (`slice-image.ts`, the Room-creation Server Action), and produces a **visually indistinguishable** result to a Participant. The mask approach is strictly less work for the same visible outcome, and is actually *more* robust at extreme zoom (a vector path recomputed per render stays crisp; a fixed-resolution bitmap cut server-side would not).
- **No schema/migration/Server Action changes anywhere in this story.** Everything needed (`gridRow`/`gridCol`/`gridRows`/`gridCols`) is already on the client payload (`RoomDetailPiece`, `src/lib/rooms/get-room-by-slug.ts`).

### Current state of the file being modified

`src/components/canvas/room-canvas.tsx`'s `PieceSprite` (lines ~239-291 as of this story's creation) currently renders three states based on `usePieceImage`'s load status:
- `"loaded"` → `<KonvaImage image={...} {...commonProps} />`
- `"loading"` → a solid `<Rect fill="#eee6da" {...commonProps} />` placeholder
- `"error"` → a dashed-outline `<Rect stroke="#c4b8a8" dash={[6,4]} {...commonProps} />`

`commonProps` already includes `rotation: piece.rotation`, `width`/`height: tileWidth`/`tileHeight`, and `offsetX/Y` centering the piece on its own midpoint. All three branches need the new `clipFunc` added to `commonProps` (or applied individually) — none should be skipped, per AC #6.

### Reused existing patterns — do not reinvent

- **Seeded PRNG**: `src/lib/piece-cutting/seeded-scatter.ts` already has a mulberry32 implementation seeded by the Room's id, used today only for initial scatter positions. Reuse it (or its exact algorithm) for the edge-type generator's determinism — don't add a second PRNG implementation.
- **`PieceShape` (Corner/Edge/Interior) vs. this story's new `EdgeShape` (flat/tab/blank)**: these are two different, deliberately independent concepts. `classifyPieceShape` (`src/lib/piece-cutting/classify-piece-shape.ts`) answers "how many of this piece's sides are on the Frame's outer boundary" — used for FR6 validation and untouched by this story. This story's new per-*edge* (not per-piece) classification only answers "does this specific edge protrude or recess, purely visually." A boundary edge is always `EdgeShape: "flat"`, corresponding to (but not replacing) `classifyPieceShape`'s notion of which sides have no neighbor.
- **`computeAdjacency`** (`src/lib/piece-cutting/compute-adjacency.ts`) already enumerates every true orthogonal-neighbor pair exactly once (row-major, only "down"/"right" to avoid duplicates) — the new edge-type generator's canonical-key logic should mirror this exact "smaller coordinate wins" convention for consistency, though it does not need to literally call `computeAdjacency` (that function returns *pairs*, not per-piece edge lookups; recomputing the canonical key inline, per edge, per piece, is simpler than joining against the full pairs list).
- **"Reasonable default, tune during manual testing" constants**: this codebase has an established convention (see `CONTACT_TOLERANCE_FACTOR`, `NEARBY_LOCK_MARGIN_FACTOR` in `piece-actions.ts`) of a named constant + comment marking it as non-spec-mandated, meant to be tuned once the feature is visually running. Follow this for the tab bump size/depth constant(s) in Task 2 — do not treat the exact visual proportions as something to get "correct" analytically up front.

### Architecture compliance

- No Server Action, RLS policy, schema, or migration changes — this is Canvas-rendering-only, entirely client-side, matching AD-2 (server-authoritative writes — none happen here) and this story's own AC #5.
- AD-3 (precomputed adjacency graph, zero client-side geometric recomputation for *validation*) is unaffected — this story adds a second, independent piece of precomputation (edge visual shape), but it is never consulted by any validation path, only by rendering.
- Vocabulary table: `PieceShape` (Forme élémentaire) already exists in the fixed vocabulary; this story's new "edge shape" concept is a rendering-only addition with no French-vocabulary counterpart yet established — pick clear English identifiers (`EdgeShape`, `computePieceEdgeShapes`) and don't overload `PieceShape`'s existing meaning.

- **Real bug found via user report, fixed (2026-09-03): `clipFunc` has no effect on a Konva `Shape`.** The first version attached `clipFunc` directly to the `KonvaImage`/`Rect` (a `Shape`) — Konva's own source (`Container.js`'s `_drawChildren`) shows `clipFunc` is only ever read on `Container` (Group/Layer), never on `Shape`; a Shape silently ignores it. The user reported seeing no visual change at all after deploying, which is exactly the symptom of a no-op clip. Fixed by making `PieceSprite`'s root node a `<Group>` (carrying position/rotation/drag/click/`clipFunc`) wrapping a plain, un-transformed child Image/Rect — the same "draggable Group, non-draggable child Shape, events bubble up" pattern `ClusterGroupSprite` already used for its own members, so drag/click behavior is unchanged. This is a real, user-facing regression fix, not a refinement — confirms this story's own honesty about not having verified the visual result was warranted; the first implementation genuinely didn't work.
- **Second real bug found via user report, fixed (2026-09-03): the bump's tip pinched.** The original two-quadratic-curve bump joined its curves at the apex using control points offset to 1.1× the apex's own depth — the two curves' tangents didn't match at that join, leaving a visible dimple right at the tip of *every* bump, tab or blank alike. A "tab" therefore read as a small notch instead of a clean outward bulge, and since the artifact looked similar regardless of which type it technically was, every piece appeared to show only "notches," all looking alike — matching the user's exact report ("il n'y a que les encoches... toutes identiques"). Replaced with a single quadratic Bezier per bump (control point at exactly 2× depth, the standard formula for a quadratic curve's midpoint to land at a target depth) — a single quadratic Bezier is mathematically guaranteed simple/non-self-intersecting, so this class of bug cannot recur by construction, not just by tuning. Added a regression test (`build-piece-outline-path.test.ts`, "never self-intersects") asserting the control point's offset genuinely exceeds the endpoint's for both tab and blank.
- **Third real bug found via user report, fixed (2026-09-03): a tab had no real pixels to reveal.** `KonvaImage`/`Rect` never paint outside whatever box they're given — a tab's clip protrudes past a piece's own `tileWidth × tileHeight` rectangle, and clipping to a region the image was never drawn into just reveals transparency, regardless of how correct the clip path is. Only blanks (which recede *into* content that genuinely exists) could ever show; this is a fundamental gap in "plain rectangular tiles + client-side mask" for the *outward* case specifically, not a code bug in the geometry or the clip wiring — both of those were already correct by this point. Asked the user to choose between three fixes (widen the creation-time slice for real neighboring pixels / stretch each piece's own image as an approximation / drop tabs and keep only blanks); user chose widening the slice. Implemented in `slice-image.ts` (`TILE_OVERHANG_FACTOR = 0.25`, sampling genuine bitmap content beyond each tile's own footprint, clamped at the source image's true edges) and `PieceSprite` (sizes the loaded image from its own `naturalWidth`/`naturalHeight` rather than assuming padding exists) — see Change Log for the full reasoning and the accepted limitation for already-existing Rooms.
- **Confirmed working by the user (2026-09-03) on a newly-created Room** — tabs now render with real neighboring content, resolving all three bugs above. Still not independently verified in this environment (no browser/screenshot tooling): whether a tab renders on top of the correct neighbor rather than being occluded by it, and whether rotation truly composes as a rigid transform, remain open per the user's own manual testing rather than anything checked here.
- **Enhancement, user-requested (2026-09-03): bump variety, "donner l'impression de diversité."** Every tab/blank previously used one fixed depth/neck-width/position — every bump on every piece looked identical. Added a table of 15 "bump profiles" (`BUMP_PROFILES` in `build-piece-outline-path.ts`, varying depth, neck width, and a small lateral offset from the edge's midpoint) and a second deterministic draw per shared edge (`profileSeed`, `compute-piece-edge-shapes.ts`) selecting which profile applies — from the *same* freshly-seeded PRNG stream the tab/blank decision already uses, so both pieces sharing an edge independently derive the identical profile (required: a tab and its complementary blank must match in size/position, or they wouldn't visually fit together — verified directly by a new test, "gives every interior edge a complementary shape AND the same profile between true neighbors"). `TILE_OVERHANG_FACTOR` (0.25) comfortably exceeds the deepest profile's `depthFactor` (0.20) with margin, so the deepest tab still has real pixels to reveal.
- **Visual refinement, user feedback with a reference image (2026-09-04): "plus ressemblantes au languettes encoches d'un vrai puzzle."** The single-quadratic-curve bump (a plain symmetric dome) never actually narrows anywhere, so it never reads as a puzzle knob no matter how it's sized — real puzzle tabs have a narrow neck flaring into a bulb *wider than the neck itself*. Redesigned each bump's `neckWidthFraction` (renamed from the old single width) and added a separate, always-larger `bulbWidthFraction` per profile; the geometry itself changed from one quadratic curve to two mirrored cubic Beziers per bump (neckStart→apex, apex→neckEnd), each pulled laterally out to the bulb's width partway through its own depth before curving back toward the centerline at the apex — this is what produces the actual narrow-neck/wide-head silhouette. Added `PathCommand`'s `bezierCurveTo` variant and `PathDrawingContext.bezierCurveTo` (Konva's `Konva.Context` already supports it with a matching signature, confirmed against `node_modules/konva/lib/Context.d.ts`, so still no cast needed). New test asserts the concrete visual invariant this was all for: the bulb's control points genuinely extend further from center than the neck's own half-width, across the whole profile table.
- **Follow-up visual fix, same day (user feedback: "il faut arrondir la pointe"):** the two cubic curves' control points nearest the apex sat at only 92% of the apex's own depth — the incoming tangent (still rising toward the apex) and outgoing tangent (already falling away from it) disagreed at the join, leaving a visible point/cusp right at the tip instead of a smooth round top. Fixed by moving those two control points to the *exact same depth* as the apex — both tangents become purely lateral (horizontal) right at the join, meeting smoothly like the top of a circle. New regression test (`build-piece-outline-path.test.ts`, "meets smoothly at the apex") asserts this depth equality directly, across the profile table.
- **Fourth real bug found via user feedback, fixed (2026-09-04): tabs/blanks didn't line up between neighbors.** `BUMP_PROFILES` originally included a `centerOffsetFraction`, shifting each bump's lateral position from the edge's exact midpoint for extra variety. Missed: two pieces sharing an edge walk it in *opposite* directions by this module's own traversal convention (a piece's "right" edge runs top→bottom; its right neighbor's "left" edge — the same physical line — runs bottom→top). A lateral offset measured "along the direction of travel" therefore pushed the bump toward *opposite physical ends* of the shared edge for the two neighbors, even though both independently derive the identical profile (same depth/neck/bulb) — every non-zero offset was a guaranteed misalignment, not an occasional one. The user's own suggested fix ("il suffirait pourtant de tous les laisser au milieu") was exactly right and is what's implemented: `centerOffsetFraction` removed entirely, every bump now centers on the edge's exact midpoint, which is direction-invariant by construction — variety is still preserved via depth/neck-width/bulb-width, none of which have this directional sensitivity. New regression test (`build-piece-outline-path.test.ts`, "aligns identically for two neighbors walking the same shared edge in opposite directions") builds both a "right" and a "left" edge with the same profile and asserts their apex lands at the identical physical position.
- **Final user confirmation (2026-09-04): "on est bon."** All acceptance criteria satisfied on a newly-created Room, across four rounds of real user-driven bug-fixing (clip-on-Shape no-op, curve pinch, missing tab pixels, misaligned centers) plus one requested enhancement (bump variety) — every fix traced back to a concrete, reproduced symptom the user actually observed, not a hypothetical. `pnpm build`/`pnpm lint`/`pnpm test` clean throughout (203 tests, 26 files, final count).
