# Story 3.5: Place a piece into the Frame with real geometric validation

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a Participant,
I want to drag a piece toward the Frame and have it snap in only when it truly belongs there,
so that assembling the puzzle feels like a real physical puzzle, not an arbitrary click-to-place.

## Acceptance Criteria

1. A Participant can drag any piece freely around the infinite Canvas (mouse or touch), independent of panning/zooming the Canvas itself.
2. Tapping (mobile) or clicking (desktop) a piece rotates it by a fixed 90° increment. (Revised 2026-08-31, user-requested: originally double-tap/double-click — see Change Log (8).)
3. Dropping a piece at a Frame location whose slot category (Corner/Edge/Interior) matches the piece's `PieceShape`, **and** whose edges genuinely match any already-placed neighboring pieces (per the precomputed `PieceAdjacency` graph), snaps the piece into place automatically — no manual confirmation step.
4. The system never checks a piece's *position* against the source image — a Corner piece can be dropped into any corner slot and stay there until its edges are tested against neighbors (user-confirmed, 2026-08-27: position is deliberately never validated, matching the PRD's physical-puzzle-like discovery mechanic).
5. The system *does* check a piece's **orientation**: a piece only snaps into place at `rotation === 0°` (its as-cut, canonical upright orientation) — dropping a correctly-shaped, correctly-adjacent piece that is rotated 90/180/270° does not snap it in (user-confirmed, 2026-08-27; see Dev Notes for why this doesn't contradict AC #4).
6. Dropping a piece where its shape, adjacency, or orientation doesn't validate leaves it exactly where released — never erratically flung or lost off-canvas (NFR-1).
7. Validation runs authoritatively on the server (a Server Action, consulting the precomputed `PieceAdjacency` graph) — a client may optimistically predict the result, but never determines it alone (AD-2, NFR6).
8. The updated Frame state is visible to every Participant present with no perceptible delay (FR-3) — via real-time Supabase Realtime (`postgres_changes`) synced through a custom TanStack DB collection (Architecture AD-1, amended 2026-08-28), not a page-reload or polling.

## User-confirmed scope decisions (2026-08-27/28)

- **Position is never validated; orientation is.** FR-6/the epics AC are explicit that position-checking is off the table entirely (it would require comparing against the source image, which the whole game is built to avoid). Orientation is different: because every piece tile is sliced directly from the source image with `rotation = 0` being its as-cut, correct-looking orientation, checking `rotation === 0` at placement time requires no hidden "answer" data at all — it's not a disguised position check, it's confirming the piece looks right, which the family can already see with their own eyes without any server help. The user explicitly chose "verify orientation, not position" after discussing the trade-off (position-checking would remove the "discover the right spot only by testing neighbors" mechanic FR-6 is built around).
- **A whole-Frame re-orientation mechanic is explicitly out of scope for this story, noted for a future one.** Since position is never validated, the *entire* assembled arrangement (not just one piece) could in principle end up built 180°-rotated or mirrored relative to the Frame's fixed axes, even though every individual piece is at its own correct `rotation = 0` — adjacency alone doesn't distinguish the whole assembly's global orientation. The user asked for this to be tracked, not solved now: **do not build a "rotate all placed pieces" mechanic in this story.** Nothing in this story's schema (`placed_row`/`placed_col`, independent per piece) blocks adding it later — a future story would just need a Server Action remapping every placed piece's slot through the chosen transform in one atomic transaction. Add a `deferred-work.md` entry for this; do not attempt it here.
- **Live sync uses Supabase Realtime, not ElectricSQL — this decision was reversed mid-stream (2026-08-28/29), after Story 1.1 originally deferred ElectricSQL provisioning "to whichever story first genuinely needs it — almost certainly Story 3.5."** Between that decision and this story's creation, Databricks acquired ElectricSQL (2026-08-11) and is winding down Electric Cloud (the managed hosted product) entirely — existing customers were told to self-host or migrate. The open-source sync engine itself remains maintained (Apache 2.0), but self-hosting it is a real, ongoing operational burden for a solo-dev project, and no managed successor exists yet (Databricks/Neon have said they're building Electric-powered sync into Neon, but nothing is shipped or priced today). The user chose Supabase Realtime instead: **zero new vendor** (already part of the Supabase project this app already depends on for Auth/Storage/DB), free at this app's scale (free tier: 200 concurrent connections, 2M messages/month), and architecturally sound for the same reason Electric was — it's a `postgres_changes` stream the client subscribes to read-only, never a channel for direct writes. **`ARCHITECTURE-SPINE.md`'s AD-1/AD-2/AD-6/AD-7 have been amended accordingly (2026-08-28)** — the underlying principle (one shared read-sync channel, server-authoritative writes, no polling, no parallel channel) is unchanged; only the concrete transport is different. Other technologies considered and rejected during this detour: self-hosting Electric (too much ops burden for the gain), PowerSync (genuinely good architectural fit — clients call a backend `uploadData()` endpoint rather than writing directly, matching AD-2 — but its free tier deactivates inactive projects after 1 week, a bad fit for a family app used in occasional bursts, and it's still a new vendor/account), RxDB (its Supabase plugin assumes direct client writes via PostgREST + RLS, which contradicts AD-2 outright and would require moving FR-6 validation into RLS/triggers), plain polling (too much lag for "no perceptible delay").
- **Rotation before placement is a synced field, not a local-only gesture.** So other Participants see a piece mid-rotation (or already rotated) before it's placed, rotation changes go through the same Server Action → Postgres → Realtime round-trip as position/placement changes — not just a client-local Konva transform. This keeps a single source of truth per Architecture AD-1 ("aucune mutation optimiste appliquée directement, réconciliation exclusivement via" the Realtime stream).
- **Proximity threshold for "close enough to a Frame slot to attempt validation" is an implementation decision** (the PRD explicitly flags this as unspecified — "seuil de proximité... assumption to be defined downstream"). This story picks: a piece's drop point snaps to the nearest Frame slot if the drop point's distance from that slot's center is within half a tile's width/height (i.e., the drop point is closer to that slot than to any adjacent one). This is a reasonable, tunable default — revisit if manual testing shows it feels wrong.

  - [x] All three share the same optimistic-concurrency shape: accept `expectedVersion: number`; inside a single transaction, `select ... for update` the target `piece` row, compare `version`, and if mismatched, `ROLLBACK` and return `{ success: false, error: { code: ERROR_CODES.STALE_WRITE } }` — **never silently overwrite** (AD-6, verbatim).   - [x] Every one of these three is a **single atomic Postgres transaction** — no sequence of separate round-trips the client could observe halfway through (mirrors AD-3's explicit requirement for Cluster fusion; the same reasoning applies to any multi-row-implication mutation).

Concretely: every Server Action in this story returns `{ success: true, version: newVersion }`, and the client-side mutation handler's job is to wait for that piece's `version` to actually arrive via the Realtime-fed `sync()` before resolving — not to trust `{success: true}` and move on. Getting this wrong doesn't show up as a build error or even an obvious runtime error; it shows up as "works for the person who clicked it, silently diverges for everyone else," which is exactly the bug class AD-1 exists to prevent.
- **Why orientation-checking doesn't contradict "never check against the source image":** every piece's stored tile image is sliced directly from the source photo at `rotation = 0`; that's not derived from or dependent on knowing the piece's correct grid position (the actual hidden "answer"). Checking `rotation === 0` only confirms the piece is displayed the way it was cut — something already visible to the Participant without server help — never anything about *where* it belongs. This is the load-bearing distinction the whole story's validation design rests on; don't blur it by, for instance, "helpfully" telling a Participant which rotation is correct before they've achieved it themselves.
- **The proximity-threshold and whole-Frame-rotation items are both explicitly flagged, tunable/deferred choices, not settled requirements** — see User-confirmed scope decisions above. Don't over-invest in either; the threshold can be adjusted with a one-line constant change later, and the whole-Frame-rotation mechanic is intentionally not this story's problem.
- **This is the first story to use Supabase Realtime or TanStack DB for anything — and the Realtime choice itself was a mid-stream pivot, not the original plan.** The story was first drafted around ElectricSQL Cloud; Databricks' acquisition and Electric Cloud's shutdown (both 2026-08-11 onward) happened *during this story's creation*, before any code was written, and `ARCHITECTURE-SPINE.md` was amended accordingly (2026-08-28) before this rewrite. `@tanstack/db`/`@tanstack/react-db` are still used (Story 1.1 bootstrap dependencies) but `@tanstack/electric-db-collection` is **not** — this story writes a fully custom `sync` instead (see Task 6). Read `@tanstack/db`'s current version/API in `package.json`/its docs before assuming any specific shape; the architecture's risk register still flags it pre-1.0 as an accepted velocity trade-off.
- **No new Route Handler in this story.** The original Electric-based plan needed one to keep a secret off the client; Supabase Realtime doesn't have that problem (publishable key + existing RLS `SELECT` policy is the whole story), so Task 5 was removed outright rather than repurposed. If this project's first genuine Route Handler need shows up in a later story, it isn't blocked by anything here.
- **Reuse, don't reinvent:** `classifyPieceShape` (Story 2.4) for shape-category checks, `computeAdjacency`'s already-persisted `piece_adjacency` rows (not a live recomputation) for neighbor truth, the Frame's centered-on-origin coordinate convention (Story 3.1) for placed-piece pixel positioning, and Story 3.3's `isDraggable`-state-toggle pattern for Stage-vs-piece drag coexistence. This story adds a lot of genuinely new infrastructure (Realtime, a custom TanStack DB collection, error-code registry) — don't also reinvent things that already exist.
- **No sound/animation/haptics in this story** — that's Story 3.6 (Placement feedback) specifically. A successful placement in this story is a plain, instant, silent snap. Resist adding polish here.
- **No Cluster/Îlot logic in this story** — Stories 3.8/3.9/3.10 own piece-to-piece fusion away from the Frame. This story's "edges genuinely match" check only ever compares a piece being placed against *already-Frame-placed* neighbors, never against other free-floating pieces.
